จุดประสงค์

ประเมินคุณภาพของแอปตนเองตามมาตรฐานและด้วย Lighthouse และปรับปรุงการเข้าถึงได้ พร้อมหลักฐานก่อนและหลัง

คำชี้แจง

ฝึกแก้ปัญหาการเข้าถึงจากฟอร์มตัวอย่างที่ตั้งใจให้มีปัญหา เขียนการทดสอบที่พิสูจน์ว่าแก้แล้ว จากนั้นประเมินและปรับปรุงแอปของตนเอง รันการทดสอบในเทอร์มินัลหน้าต่างที่ 2 (ไม่ต้องปิด ionic serve)

สิ่งที่ต้องเตรียม

  • ใบความรู้ที่ 8 หัวข้อคุณภาพและการเข้าถึง
  • Chrome (สำหรับ Lighthouse)

  1. สร้างไฟล์ src/components/BadForm.tsx วางโค้ดนี้ทั้งไฟล์ กด Ctrl+S (ฟอร์มนี้ตั้งใจให้มีปัญหาด้านการเข้าถึง 5 จุดขึ้นไป)

    ไฟล์ src/components/BadForm.tsx
    import { useState } from 'react';

// ฟอร์มนี้มีปัญหาด้านการเข้าถึงอย่างน้อย 5 จุด ให้ค้นหาและแก้ไข
const BadForm: React.FC = () => {
  const [title, setTitle] = useState('');
  const [items, setItems] = useState<string[]>([]);

  function add() {
    if (title.trim() === '') return;
    setItems([...items, title.trim()]);
    setTitle('');
  }

  return (
    <div>
      <div style={{ fontSize: 24 }}>รายการของฉัน</div>

      <input placeholder="ชื่อรายการ" value={title} onChange={e => setTitle(e.target.value)} />

      <div
        style={{ background: '#7fbf7f', color: '#ffffff', padding: 6, display: 'inline-block' }}
        onClick={add}
      >
        เพิ่มรายการ
      </div>

      <span onClick={() => setItems([])} style={{ cursor: 'pointer' }}>
        ✕
      </span>

      <ul>
        {items.map(i => (
          <li key={i}>{i}</li>
        ))}
      </ul>

      <img src="logo.png" />
    </div>
  );
};

export default BadForm;
    ผลที่ควรเห็น: ไม่มีข้อความแดง

  3. สร้างไฟล์ทดสอบ src/components/BadForm.test.tsx วางโค้ดนี้ทั้งไฟล์ กด Ctrl+S (การทดสอบหาองค์ประกอบแบบเดียวกับที่โปรแกรมอ่านหน้าจอมองเห็น)

    ไฟล์ src/components/BadForm.test.tsx
    import { fireEvent, render, screen } from '@testing-library/react';
import { describe, expect, it } from 'vitest';
import BadForm from './BadForm';

describe('BadForm (การเข้าถึง)', () => {
  it('มีหัวเรื่องที่โปรแกรมอ่านหน้าจอรู้จัก', () => {
    render(<BadForm />);
    expect(screen.getByRole('heading', { name: 'รายการของฉัน' })).toBeInTheDocument();
  });

  it('ช่องกรอกมีป้ายชื่อ', () => {
    render(<BadForm />);
    expect(screen.getByLabelText('ชื่อรายการ')).toBeInTheDocument();
  });

  it('ปุ่มเพิ่มรายการเป็นปุ่มจริง', () => {
    render(<BadForm />);
    expect(screen.getByRole('button', { name: 'เพิ่มรายการ' })).toBeInTheDocument();
  });

  it('ปุ่มล้างรายการมีชื่อที่อ่านออกเสียงได้', () => {
    render(<BadForm />);
    expect(screen.getByRole('button', { name: 'ล้างรายการทั้งหมด' })).toBeInTheDocument();
  });

  it('รูปภาพมีข้อความแทน', () => {
    render(<BadForm />);
    expect(screen.getByAltText('โลโก้แอป')).toBeInTheDocument();
  });

  it('เพิ่มรายการแล้วแสดงในรายการ', () => {
    render(<BadForm />);
    fireEvent.change(screen.getByLabelText('ชื่อรายการ'), { target: { value: 'ข้าวมันไก่' } });
    fireEvent.click(screen.getByRole('button', { name: 'เพิ่มรายการ' }));
    expect(screen.getByRole('listitem')).toHaveTextContent('ข้าวมันไก่');
  });
});
    ผลที่ควรเห็น: ไม่มีข้อความแดง (ถ้าตัวแก้ไขขีดแดงที่ toBeInTheDocument ให้รันขั้นต่อไปก่อน)

  14. รัน Lighthouse: ใน Chrome กด F12 เลือกแท็บ Lighthouse เลือก Mobile ติ๊ก Performance, Accessibility, Best practices แล้วกดปุ่ม Analyze page load

  15. อ่านรายการปัญหาในส่วน Accessibility และ Best practices ที่ Lighthouse แสดง (กดที่แต่ละข้อเพื่อดูรายละเอียดและองค์ประกอบที่เกี่ยวข้อง) เลือกปัญหาที่พบในแอปคุณอย่างน้อย 5 จุด

    ผลที่ควรเห็น: ได้รายการปัญหา 5 ข้อพร้อมที่ตั้งในโค้ด

  16. ตรวจ index.html ของโปรเจกต์: ถ้ามีแท็ก viewport ที่มีค่า maximum-scale=1.0 และ user-scalable=no ซึ่งปิดการซูมของผู้ใช้ ให้พิจารณาลบสองค่านี้ออก (ผู้ที่สายตาไม่ดีใช้งานลำบาก Lighthouse จะเตือนข้อนี้) บันทึก แล้วตรวจว่าหน้าจอยังแสดงถูกต้องเมื่อซูม

    ผลที่ควรเห็น: แท็ก viewport เหลือ width=device-width, initial-scale=1.0 และ Lighthouse ไม่เตือนข้อซูมอีก (ถ้าโปรเจกต์ของคุณมีค่าเหล่านี้อยู่)

  17. แก้ปัญหาที่ Lighthouse พบในแอปตนเองอย่างน้อย 5 จุด (เช่น ป้ายชื่อช่องกรอก aria-label ของปุ่มไอคอน สีที่ความต่างไม่พอ ข้อความแทนของรูป) แล้วสร้างเวอร์ชัน build ใหม่และวัด Lighthouse ซ้ำ

    ผลที่ควรเห็น: ได้คะแนนก่อนและหลัง คะแนน Accessibility สูงขึ้นหรือเท่าเดิมโดยมีเหตุผลอธิบาย

  18. ทดสอบด้วยแป้นพิมพ์: ในหน้าของแอป ใช้ปุ่ม Tab ผ่านทุกฟังก์ชันของ use case หลัก 2 ข้อโดยไม่ใช้เมาส์ (Enter หรือ Space เพื่อกดปุ่ม) บันทึกปัญหาที่พบ เช่น กดไม่ได้ ลำดับสลับ ไม่เห็นกรอบโฟกัส

    ผลที่ควรเห็น: ได้รายการปัญหาจากการใช้แป้นพิมพ์ (หรือบันทึกว่าไม่พบปัญหา)

  19. ทดสอบกับโปรแกรมอ่านหน้าจอ (TalkBack บน Android, VoiceOver บน iPhone หรือ NVDA บนคอมพิวเตอร์ อย่างใดอย่างหนึ่ง) บันทึกสิ่งที่ได้ยินและปัญหา ถ้าไม่มีเครื่องมือให้เขียนว่าไม่ได้ทดสอบ และเหตุผล

    ผลที่ควรเห็น: ได้บันทึกผลการฟัง หรือคำอธิบายว่าไม่ได้ทดสอบ

  20. ประเมินคุณภาพตาม ISO/IEC 25010:2023 ครบ 9 ข้อ ในตารางไฟล์ Word: คุณลักษณะ / คำถามที่ใช้ / ผลการประเมิน (ดี พอใช้ ต้องปรับปรุง) / หลักฐาน (ผลทดสอบ คะแนน ภาพ) / ข้อเสนอแนะ

    ผลที่ควรเห็น: ตาราง 9 แถวมีหลักฐานทุกแถว

  21. ให้เพื่อน 2 คนลองใช้แอปทำงานหลัก 1 งานโดยไม่อธิบายก่อน สังเกตจุดที่ติดขัด แล้วเทียบกับหลักการของ Nielsen อย่างน้อย 3 ข้อ บันทึกในตาราง

    ผลที่ควรเห็น: ได้ตารางจุดที่ติดขัดจากเพื่อน 2 คน เทียบ 3 หลักการ

    ผลที่ควรเห็น: ได้แผน 5 ข้อ
