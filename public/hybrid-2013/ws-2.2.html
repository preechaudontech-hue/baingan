ใบงานที่ 2.2 Use Case Diagram ของแอป

เวลา 90 นาที · งานเดี่ยว · คะแนนเต็ม 10

จุดประสงค์

วาด Use Case Diagram ของแอปตนเองด้วยสัญลักษณ์ที่ถูกต้อง

คำชี้แจง

นำผลงานใบงาน 2.1 มาสร้าง Use Case Diagram ใช้ตัวอย่าง MyExpense เป็นแบบ วาดด้วยมือบนกระดาษแล้วถ่ายภาพ หรือวาดด้วยโปรแกรมก็ได้ ครูมีแบบฟอร์มวาดสำหรับดาวน์โหลดไว้ในหน้าใบงานนี้ ก่อนวาดให้เขียนรายการทุกอย่างเป็นตัวอักษรก่อน เพราะวาดตามรายการจะเร็วและผิดน้อยกว่า

ดาวน์โหลดแบบฟอร์ม

แบบฝึก Use Case Diagram (ไฟล์ Word 5 หน้า) คลิกเพื่อดาวน์โหลด

สิ่งที่ต้องเตรียม

  • ผลงานใบงาน 2.1
  • ใบความรู้ที่ 2 หัวข้อ Use Case Diagram

ขั้นตอนการปฏิบัติ

  1. เปิดผลงาน 2.1 แล้วหาคำว่า ผู้ใช้ ใน user story ทั้ง 6 ข้อ เขียนรายการบทบาทที่ไม่ซ้ำกันทั้งหมด

    ผลที่ควรเห็น: ได้รายการ เช่น ผู้ใช้ (หรือ นักเรียน ถ้า story ใช้คำนี้) อย่างน้อย 1 บทบาท

  2. ถามว่ามีระบบภายนอกที่แอปต้องคุยด้วยหรือไม่ (เช่น API สภาพอากาศ ระบบล็อกอินของ Google) ถ้ามีให้เพิ่มเป็น actor อีกตัว ถ้าไม่มีให้เขียนว่า ไม่มี

    ผลที่ควรเห็น: ได้รายการ actor สุดท้าย เช่น ผู้ใช้ 1 ตัว (ไม่มีระบบภายนอก)

  3. เขียนชื่อ use case จาก user story ข้อที่ 1 โดยตั้งชื่อเป็นกริยานำ ไม่เกิน 3-4 คำ

    ผลที่ควรเห็น: ได้ชื่อ เช่น เพิ่มรายจ่าย (ไม่ใช่ ระบบเพิ่มรายจ่ายให้ผู้ใช้)

  4. เขียนชื่อ use case จาก user story ข้อที่ 2 ถึง 6 ทีละข้อ ข้อละ 1 ชื่อ

    ผลที่ควรเห็น: ได้ชื่อ use case อย่างน้อย 6 ชื่อ เช่น เพิ่มรายจ่าย ดูรายการรายจ่าย ลบรายจ่าย แก้รายจ่าย ดูสรุปรายเดือน ค้นหารายการ

  5. ตรวจว่า use case ระดับ Must จากตาราง MoSCoW ใน 2.1 ถูกครอบคลุมครบทุกข้อ ถ้ามีข้อที่ตกหล่นให้เพิ่ม use case

    ผลที่ควรเห็น: ทุกข้อ Must มี use case อย่างน้อย 1 อัน

  6. เตรียมเครื่องมือวาด: บนกระดาษ ให้ใช้ดินสอและไม้บรรทัด วาดสี่เหลี่ยมใหญ่ 1 รูปไว้กลางหน้า ถ้าวาดด้วยโปรแกรม: เปิดเว็บ app.diagrams.net (ชื่อเดิม draw.io) ในเบราว์เซอร์ เลือกที่เก็บไฟล์เป็น Device (เครื่องของคุณ) แล้วเลือก Create New Diagram เลือก Blank Diagram ตั้งชื่อไฟล์แล้วกด Create (ชื่อเมนูอาจต่างเล็กน้อยตามเวอร์ชัน)

    ผลที่ควรเห็น: มีพื้นที่ว่างสำหรับวาด

  7. วาดขอบเขตระบบ: เขียนสี่เหลี่ยมใหญ่และเขียนชื่อแอปไว้บนขอบด้านบนของสี่เหลี่ยมนั้น (ในโปรแกรม ใช้รูปร่าง Rectangle ลากให้ใหญ่ แล้วพิมพ์ชื่อ)

    ผลที่ควรเห็น: ได้สี่เหลี่ยมที่มีชื่อแอปด้านบน

  8. วาด use case ลงในสี่เหลี่ยม: วาดวงรีตามจำนวน use case ในข้อก่อน เขียนชื่อในวงรี เรียงเป็นแถวตั้งหรือสองคอลัมน์เว้นระยะให้พอลากเส้น (ในโปรแกรม ใช้รูปร่าง Ellipse)

    ผลที่ควรเห็น: วงรีทุกวงอยู่ภายในสี่เหลี่ยม ไม่ทับกัน อ่านชื่อออก

  9. วาด actor นอกสี่เหลี่ยม: วาดคนไม้ไว้ด้านซ้ายของสี่เหลี่ยม เขียนชื่อบทบาทไว้ใต้ตัวคนไม้ (ในโปรแกรม ค้นหาคำว่า actor ในช่องค้นหารูปร่างด้านซ้าย)

    ผลที่ควรเห็น: คนไม้อยู่นอกสี่เหลี่ยม มีชื่อบทบาทใต้ตัว

  10. ลากเส้นตรงจาก actor ไปยัง use case ที่ actor นั้นใช้ทีละอัน (association) เส้นละ 1 use case

    ผลที่ควรเห็น: เห็นเส้นเชื่อมจาก actor ถึงทุกวงรี และไม่มีวงรีที่ไม่มีเส้นเชื่อมเลย (ยกเว้น use case ที่ถูก include)

  11. หา use case ที่ต้องทำเสมอทุกครั้งที่ทำอีก use case หนึ่ง เช่น การตรวจความถูกต้องของข้อมูลทุกครั้งที่เพิ่มรายจ่าย แล้วเพิ่มวงรีใหม่ชื่อ ตรวจความถูกต้องของข้อมูล

    ผลที่ควรเห็น: มีวงรีใหม่ 1 วง

  12. ลากลูกศรเส้นประจากวงรี เพิ่มรายจ่าย ไปหาวงรี ตรวจความถูกต้องของข้อมูล เขียนคำว่า <<include>> กำกับเส้น (ปลายลูกศรชี้ไปที่ use case ที่ถูกเรียกใช้)

    ผลที่ควรเห็น: ลูกศรเส้นประมีคำว่า <<include>> หัวลูกศรชี้ที่ ตรวจความถูกต้องของข้อมูล

  13. เขียนเหตุผลสั้น ๆ 1 บรรทัดว่าทำไมจึงเป็น include (ต้องเรียกเสมอ) ไม่ใช่ extend (เรียกเฉพาะเมื่อมีเงื่อนไข) หรือถ้ามี use case เสริม ให้ใช้ <<extend>> แล้วเขียนเงื่อนไข

    ผลที่ควรเห็น: ได้เหตุผล เช่น ทุกครั้งที่เพิ่มรายจ่ายต้องตรวจข้อมูลก่อนเสมอ จึงใช้ include

  14. ถอยห่างจากภาพ 1 เมตร แล้วตรวจ 4 ข้อ: actor อยู่นอกกรอบ use case อยู่ในกรอบ ทุกชื่อ use case ขึ้นต้นด้วยกริยา และไม่มีเส้นไขว้กันโดยไม่จำเป็น แก้ข้อที่ไม่ผ่าน

    ผลที่ควรเห็น: ผ่านทั้ง 4 ข้อ

  15. บันทึกหรือถ่ายภาพไดอะแกรม (ในโปรแกรม ใช้เมนู File แล้ว Export as เลือก PNG)

    ผลที่ควรเห็น: ได้ไฟล์ภาพที่อ่านชื่อทุกตัวได้ชัด

  16. เลือก use case สำคัญอันที่ 1 (เช่น เพิ่มรายจ่าย) แล้วเขียนหัวข้อ ผู้กระทำ เงื่อนไขก่อนเริ่ม และเป้าหมาย 1 บรรทัดต่อหัวข้อ

    ผลที่ควรเห็น: ได้หัวข้อ 3 บรรทัด เช่น เงื่อนไขก่อนเริ่ม: เปิดแอปอยู่ที่หน้าหลัก

  17. เขียนขั้นตอนหลักของ use case แรก เป็นคู่ ๆ ทีละข้อ: ผู้ใช้ทำอะไร และระบบตอบสนองอย่างไร อย่างน้อย 4 คู่

    ผลที่ควรเห็น: ได้ขั้นตอน เช่น 1 ผู้ใช้กดปุ่ม เพิ่ม ระบบแสดงฟอร์ม 2 ผู้ใช้กรอกชื่อและจำนวนเงิน ระบบแสดงตัวอักษรที่กรอก 3 ผู้ใช้กด บันทึก ระบบตรวจข้อมูล 4 ระบบบันทึกและกลับหน้าหลักพร้อมรายการใหม่

  18. เขียนกรณีข้อผิดพลาด 1 กรณีของ use case แรก และสิ่งที่ระบบทำ

    ผลที่ควรเห็น: ได้ข้อความ เช่น ถ้าไม่กรอกจำนวนเงิน ระบบแสดงข้อความ กรุณากรอกจำนวนเงิน และไม่บันทึก

  19. ทำเช่นเดียวกันกับ use case สำคัญอันที่ 2 (หัวข้อ ขั้นตอนหลักอย่างน้อย 4 คู่ และกรณีผิดพลาด 1 กรณี)

    ผลที่ควรเห็น: ได้ขั้นตอนของ use case ที่ 2 ครบ

  20. สร้างตารางโยง 2 คอลัมน์ (use case / มาจาก user story ข้อใด) แล้วเติมให้ครบทุก use case

    ผลที่ควรเห็น: ทุกแถวมีเลข user story ข้อใดข้อหนึ่ง

  21. ตรวจสองทิศทาง: use case ใดไม่มี user story ที่มาให้ลบหรือเขียน story เพิ่ม และ user story ข้อใดไม่มี use case ให้เพิ่ม use case บันทึกสิ่งที่แก้

    ผลที่ควรเห็น: ทั้ง use case และ user story โยงกันครบ ไม่มีข้อกำพร้า

  22. รวมเป็นไฟล์เดียว: ภาพ Use Case Diagram ขั้นตอนของ use case 2 อัน และตารางโยง แล้วส่งตามช่องทางที่ครูกำหนด

    ผลที่ควรเห็น: ได้ไฟล์ส่งงาน 1 ไฟล์ที่มี 3 ส่วน

คำแนะนำ

  • แผนภาพเป็นภาพรวม ไม่ต้องเขียนขั้นตอนลงในวงรี ให้เขียนขั้นตอนแยกเป็นข้อความ
  • ชื่อ use case ต้องขึ้นต้นด้วยกริยา เช่น เพิ่มรายจ่าย ไม่ใช่ หน้าเพิ่มรายจ่าย
  • include ใช้เมื่อต้องทำเสมอ extend ใช้เมื่อทำเฉพาะบางกรณี ถ้าไม่แน่ใจให้ไม่ใช้ก่อน
  • ชื่อเมนูของ diagrams.net เปลี่ยนได้ตามเวอร์ชัน (ผู้เขียนใบงานเขียนจากความรู้ ไม่ได้เปิดโปรแกรมทดสอบทุกเมนู) ถ้าหาเมนูไม่เจอให้ถามครู

สิ่งที่ต้องส่ง

ภาพ Use Case Diagram (ภาพถ่ายหรือภาพส่งออกจากโปรแกรม) + ขั้นตอนของ use case สำคัญ 2 อัน + ตารางโยง use case กับ user story
